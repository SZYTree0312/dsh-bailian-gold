# 鲸英模式 vs 百炼成金模式：省 token 手段对比

日期：2026-09-30 · 对象：`dsh-whale-elite-preset` 与 `dsh-bailian-gold`

## 结论先说

鲸英模式的六项省 token 手段里，**三项可以借鉴、两项与缓存目标冲突、一项在百炼上是负收益**。
本次只采纳三项，另两项明确不采纳并说明理由。

## 前提：两边的省钱逻辑不同，不能照搬

| | 鲸英模式 | 百炼成金模式 |
|---|---|---|
| 省钱方式 | 减少**绝对 token 数** | 提高**缓存命中率** |
| 计费假设 | 未命中/命中价差不构成主要变量 | 命中 0.1 vs 未命中 0.8 元/百万，**8 倍** |
| 面向端点 | 原生 DeepSeek Harness | 阿里云百炼（无 `in-history`）|

**关键区别**：百炼上「省 token」和「保缓存」不是一回事。系统提示与历史都吃缓存价
（0.1 元/百万），**只有每轮新增的内容按全价计费**。所以砍掉常驻内容省的是 0.1 那一档，
收益极小；而**裁剪每轮新增的内容**（工具结果）省的是 0.8 那一档，才是真的杠杆。

## 逐项对比

| 手段 | 鲸英模式 | 百炼成金（改前） | 本次决定 |
|---|---|---|---|
| 工具面 | 8 个插件行 | 19 个插件行 | **不砍**（理由见下）|
| 工作区指令 | 不加载 | 加载，上限 131072 B | **保持加载** |
| `includeRuntimeContext` | `false` | 默认 `true` | ✅ **改为 `false`** |
| 压缩 `headroomTokens` | 32768 | 默认 65536 | **不动** |
| 压缩 `retainRatio` | 0.12 | 0.3 | **不动** |
| 工具结果裁剪 | 4096 / 2048 / 512 | 32768 / 16384 / 8192 | ✅ **收紧到 8192 / 4096 / 1024** |
| 提示词纪律 | 有（先查后写、并行调用、不写旁白） | 无 | ✅ **补上** |

## 采纳的三项

### 1. `includeRuntimeContext: false` —— 修复而非优化

`@deepseek-ai/dsh-persona` 的该字段默认 `true`，作用是注入
「ordered **dynamic** runtime context」（含 sandbox policy / approval policy / delegation），
而它落在**系统提示**里。

官方 DSH 上这没问题：系统提示变了，`systemPromptUpdate: in-history` 会把新快照
追加到缓存历史之后。**百炼两条路都拿不到 `in-history`**（端点语义不支持中间 system +
pi-ai 侧能力位 `withhold`），于是系统提示一旦变化就是**重写开头那条消息**，前缀缓存整体失效。

**代价**：该开关是全有或全无，会一并抑制静态的策略提示，没有按提供方过滤的选项。
判断是缓存安全优先——8 倍价差远大于少几条策略提示的损失，且沙箱本身仍由 harness 强制执行，
最坏情况只是模型多试一两次被拦下的操作。

鲸英模式同样关掉了它，是一个可参考的旁证。

### 2. 工具结果裁剪收紧到 8192 / 4096 / 1024

原值 32768 意味着单条工具结果最多保留 32 KB（约 8000 token）。工具结果是每轮新增内容
的主力，也是唯一按全价计费的大块：

- **直接**：当轮少发约 24 KB（6000 token）× 0.8 元/百万 ≈ 0.0048 元
- **间接**：这段内容不进历史，后续每一轮都不再重复携带
- **附带**：上下文增长变慢，压缩触发推后——而压缩会破坏前缀缓存

保留首尾（4096 + 1024）足以定位问题，中间截断。想更激进可降到鲸英模式的
4096 / 2048 / 512。

### 3. 补上提示词纪律

这是**唯一省全价 token 的行为类手段**：模型输出按输出价计费，且是当轮新增内容。
纪律里直接减少输出的几条——「不写过程旁白」「最终答复只给结论」「命令输出重定向到文件只读回需要的行」
——都在压这一块。

代价是系统提示变长，但那部分是**固定内容、吃缓存价**，一次付清、后续每轮只算 0.1。
用 0.1 的成本换 0.8 的节省，划算。

## 明确不采纳的两项

### 砍工具面（8 行 vs 19 行）

工具 schema 是**固定内容**，每轮都命中缓存，按 0.1 元/百万计费。砍掉它：
- 省下的：约 5000 token × 0.1 元/百万 × 轮数 —— 百轮约 0.05 元
- 失去的：子代理并行、workflow、plan mode、goal 追踪、web 抓取、产物呈现

**收益极小、代价明确**，不采纳。这也解释了为什么鲸英模式砍它是对的、我们不能照抄：
它的目标是压绝对 token 数，砍掉就是实打实少发；我们的目标是保缓存，砍掉省的只是缓存价那一档。

### 早压缩（`headroomTokens: 32768` + `retainRatio: 0.12`）

压缩是**唯一会主动破坏前缀缓存**的操作——一次 `replace` 会让压缩点之后的全部缓存失配。
鲸英模式要「更早压缩」以压低历史长度，在原生 DSH 上这是合理取舍（有 `in-history` 兜底，
且它追求绝对 token 数）。

在百炼上方向相反：**压缩越少越好**，靠 route 的 `contextWindow`（991808）把触发点推到
约 893504，常规会话根本压不到。参数保持 `thresholdRatio: 0.92` / `retainRatio: 0.3`。

## 顺带修正：鲸英模式里实现与描述不符的两处

对比过程中发现鲸英模式有两处「承诺与实现相反」，均已修正。**它的定位不变**，
仍是面向原生 DSH 的省 token 预设——下面两处是修 bug，不是把它改造成缓存向。

### 1. 压缩时机调反了方向

它的 README 写「`headroomTokens` 65536 → 32768，更早触发压缩」。但按
`compaction-basic/src/config.ts`：

```
pressureBudgetTokens = messageBudgetTokens − policy.headroomTokens
thresholdTokens      = min(contextWindow × thresholdRatio, pressureBudgetTokens)
```

`headroomTokens` 是从触发预算里**扣除**的余量。调小它 → `pressureBudgetTokens` 变大 →
触发点**抬高** → 压缩**更晚**。方向正好相反。

而且真正控制时机的 `thresholdRatio` 它**根本没设**（沿用默认 0.8），所以在 1M 窗口下，
`thresholdRatio` 那一侧往往才是约束项，改 `headroomTokens` 连效果都没有。

**修正**：删掉 `headroomTokens`（回到默认 65536），显式设 **`thresholdRatio: 0.6`**——
这是让「更早压缩」真正生效的唯一参数。

### 2. `retainRatio` 与触发时机无关

README 同样把它标成「更早触发压缩」。但 `retainRatio` 决定的是压缩时**保留多少尾部原文**
（压缩的深度），根本不参与触发点计算。

**修正**：取值 0.12 不变，表述改准确。

### 3. 平台提示与工具面不一致（顺带）

`persona.suffix` 里写死了「系统为 Windows，命令工具是 PowerShell」，但它的工具面
本来就做了跨平台条件（Windows 启用 `tool-pwsh`、其他平台启用 `tool-bash`）。
结果是 macOS / Linux 用户会收到**错误指引**。

**修正**：改成平台中立表述。

### 两个 preset 的边界

鲸英模式追求**绝对 token 数**，百炼成金模式追求**缓存命中率**。两者目标分歧最大的是
压缩策略：鲸英要早压缩（历史短），百炼成金要晚压缩（压缩会破坏前缀缓存）。
若将来把鲸英模式用在百炼上，需要留意这一点。

## 验证边界

本次三项改动中，第 1、3 项有源码级依据，第 2 项是计费模型的直接推论。
**但三者的实际效果都未经实机测量** —— 本仓库至今没有跑过一次真实会话。
`cached_tokens` 尚未暴露到 telemetry，所以「省了多少」目前只能说清方向，给不出数字。
